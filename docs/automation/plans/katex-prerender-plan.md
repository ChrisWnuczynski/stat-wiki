# Plan: pre-render KaTeX at build time, and split the glossary

For Grok Bot (TECH). This is read-only analysis; nothing was changed in the repo. It is based on the repo at `57a694b` and the live site on 19 Nov 2026.
Tags: **[M]** measured, **[I]** inferred.

## 1. How maths works today [M]
- `_quarto.yml` is written by `build_wiki.py` (around lines 7694–7698) with `html-math-method: {method: katex, url: /katex/}`. KaTeX **0.16.22** is vendored in `katex/` (katex.min.js, katex.min.css, fonts/).
- Pandoc emits `<span class="math inline">\(...\)</span>` / `<span class="math display">\[...\]</span>`. Quarto then adds, on every page:
  - `<script defer src="../katex/katex.min.js">`
  - a `DOMContentLoaded` loop that calls `katex.render()` on every `.math` span (`macros: []`, `throwOnError: false`)
  - a render-blocking `<link rel="stylesheet" href="../katex/katex.min.css">`
  - `window.Quarto.typesetMath`
- Other code that renders maths on demand, all of which lazy-load `katex.min.js` only if `window.katex` is missing:
  - the hover preview's `ensureKatex()`/`renderMath()` in `build_wiki.py` (around lines 3085–3108, emitted into `_random.html`)
  - the Ask widget (`ask/widget/src/browser.ts`)
- Size [M]: 115,259 math spans across the 1,700 sitemap pages. The ML article has 291 spans and the glossary 1,188 (all in `reference/glossary.html`, generated by `write_glossary()` at build_wiki.py line 5808).
- Cost on the live site (Lighthouse mobile, from this morning's audit):
  - `katex.min.js` long task: 616 ms on `articles/maximum-likelihood`, 2,527 ms on `reference/glossary`
  - TBT: 660 ms and 3,090 ms
- **Existing rendering bug found [M]:** 118 spans on about 13 pages fail to parse in KaTeX 0.16.22 because `\E`, `\Var` and `\Cov` are undefined; Quarto passes `macros: []`. Examples: `articles/cauchy-schwarz-inequality`, `designed-experiment`, `first-passage-time`, `effective-sample-size` and `marginal-and-conditional-effects`. With `throwOnError: false` they show today as red raw TeX. Fix either way, in the sources/research text or with a shared macro table (Editor decides the notation).

## 2. Approach: a post-render step using KaTeX `renderToString` (recommended)
Use a post-render step rather than a Lua filter. The Pandoc maths spans are stable in the final HTML, the site already chains post-render scripts, and it keeps Quarto's math method untouched for local preview.

**Files**
1. **New `tools/prerender_math.mjs`** (Node 22, already in `publish.yml`):
   - Walk `_site/**/*.html`, skipping `site_libs/` and the redirect stubs (`<title>Redirect</title>`).
   - Replace each `<span class="math (inline|display)">TEX</span>` with the same span wrapping `katex.renderToString(tex, {displayMode, throwOnError: true, output: "htmlAndMathml", macros: MACROS, strict: "ignore"})`. HTML-unescape TeX first (`&lt; &gt; &amp; &quot; &#39;`) and strip `\(…\)` / `\[…\]`.
   - **Keep `htmlAndMathml`.** MathML is what screen readers use. HTML-only output would be an accessibility regression [I].
   - If any span fails to parse, the build fails with file + TeX, or it writes a report and falls back to `throwOnError: false`. Pick one; failing is safer.
   - Remove `<script defer src="…katex/katex.min.js">` and Quarto's `DOMContentLoaded` render loop from the page.
   - Keep `katex.min.css` (needed for layout) and keep `window.Quarto.typesetMath`. Patch it to lazy-load KaTeX like `ensureKatex()`, or leave it, because it no-ops when `window.katex` is absent.
   - Make it idempotent: skip spans that already contain `class="katex"`.
2. **`package.json` at repo root** (or `tools/package.json`) pinning `katex@0.16.22`, the same version as `katex/`, so fonts and CSS match. Add `npm ci` in `publish.yml` before render, next to the Ask widget step.
3. **`build_wiki.py`, `_quarto.yml` template (around line 7579):** add the step to `post-render` **first**, before `canonical_redirects.py`, `search_meta.py` and `share_preview.py`, e.g. `- node tools/prerender_math.mjs` (Quarto post-render accepts any command). `search_meta.py` builds descriptions from text and already converts simple maths to plain text. Check it still reads TeX after pre-render: it must run on raw TeX, so either run `search_meta.py` before the pre-render step or have it read the MathML `<annotation encoding="application/x-tex">`. **Recommended order: canonical_redirects → search_meta → share_preview → prerender_math.**
4. **Macros:** one shared table (e.g. `tex_macros.json`), used by the pre-render step and passed to the lazy renderers (hover preview `renderMath`, Ask widget). That resolves the 118 failing spans if Editor prefers macros over editing sources.
5. **CSS:** move `katex.min.css` out of the critical path with `<link rel="preload" as="style" onload="this.rel='stylesheet'">` plus `<noscript>`. Optional; measure first, because pre-rendered maths without CSS will flash unstyled (CLS risk).

**Measured A/B on this box [M]:** the live HTML was served through a local gzip proxy (assets proxied from www.statwiki.io), comparing the original against a pre-rendered version (htmlAndMathml, katex.min.js tag and render loop removed). | articles/maximum-likelihood | today | 67 | 4.2 s | 410 ms | 2.4 s | 17,578 | 55.7 KB |
| articles/maximum-likelihood | pre-rendered | 74 | 3.7 s | 340 ms | 1.9 s | 17,580 | 78.7 KB |

Reading it:
- Pre-rendering removes the KaTeX long task: glossary TBT falls about 83% and article TBT about 17%. HTML gets bigger, by +41% gzip on the article and +60% on the glossary.
- Glossary LCP got slightly worse because of the bigger HTML.
- DOM size is unchanged, since the same KaTeX DOM now comes from the server. So **the glossary also needs splitting** (part 3).
- Rendering all 1,700 pages in Node took **6.7 s** in total [M], so build time is negligible.
- A CSS-only `content-visibility: auto` on the glossary letter sections was also tested and was **not** a win: TBT 2,040 ms with CLS 0.22 on today's page, and TBT 1,200 ms with CLS 0.07 when pre-rendered. Don't do that.

## 3. The glossary: split by letter
- [M] `reference/glossary.html` is 988 KB raw with 1,149 table rows in 27 sections (`letter-a`…`letter-z`, `letter-other`, references), 1,188 maths spans and a runtime DOM of 49.6k elements.
- [M] No page on the site links to a glossary anchor (`glossary.html#…`: 0 occurrences); 7,771 links point to `glossary.html` itself. **So splitting breaks no deep links.**
- **Change in `build_wiki.py` → `write_glossary()` (line 5808):**
  - Write `reference/glossary.qmd` as an A–Z index: letter links, entry counts, and the short description and lead it has now.
  - Write `reference/glossary/<letter>.qmd` for each letter. Merge Q/X/Z/other into neighbouring pages so each page has ≥ about 20 entries.
  - Add the new pages to the sitemap automatically (Quarto) and give them `TITLE` "Glossary: A – StatWiki" style titles. Wording goes to Editor.
  - Update the sidebar entry (`reference/glossary.qmd` stays).
  - `navbar` helpers (around lines 1650 and 1661 match `/reference/glossary/` by regex) need the new path pattern.
- **Optional:** the snippets come from `box["snippet"]` or `glossary_plain_lead()`. Using the plain-text lead for every row would cut maths spans and DOM further. That is an Editor call, since it changes what readers see.
- Lazy-rendering instead of splitting (IntersectionObserver per letter, rendering raw TeX on scroll) cuts TBT but not the DOM or HTML weight, and needs JS. **Splitting is preferred.**

## 4. Risks
1. **Visual differences:** server rendering uses the same KaTeX version, so the output should be identical, but the fonts and CSS version must match exactly (pin 0.16.22).
2. **Dynamic content:** hover previews, the Ask widget, the R runner/labs and anything injected later still need client KaTeX. They already lazy-load it via `ensureKatex()`/browser.ts. Check that labs (`labs/*.qmd`, OJS cells) don't rely on `window.katex` being present at load.
3. **Macros:** the 118 failing spans either fail the build (good, visible) or keep showing red TeX. Decide before merging.
4. **HTML weight:** +40–60% gzip on maths-heavy pages. The sidebar reduction (Repo Helper's per-topic sidebar) more than offsets it.
5. **Post-render order:** `search_meta.py` must still see raw TeX (see 2.3). `share_preview.py` and `canonical_redirects.py` are unaffected.
6. **Search engines and AI crawlers [I]:** pre-rendered pages expose maths as MathML plus an `<annotation encoding="application/x-tex">` in the raw HTML, which is better for non-JS crawlers than today's raw `\(..\)` text. It is neutral for Google, which renders JS.
7. **Dark mode:** KaTeX CSS inherits colour; check `.quarto-dark` pages.

## 5. How to verify
- **CI unit check:** run `node tools/prerender_math.mjs --check _site` in `publish.yml`. It fails if any `<span class="math …">` lacks `class="katex"` inside, or if any page still contains `katex.min.js"` as a `<script src>`.
- **Lighthouse before and after:** same 3 pages (`articles/maximum-likelihood.html`, `notes/sl-07-linkage-and-density.html`, `reference/glossary.html` or `reference/glossary/m.html` after the split), mobile, 3 runs, median. Targets:
  - TBT ≤ 350 ms on articles
  - glossary letter pages with DOM < 8k and TBT < 200 ms
  - no `katex.min.js` long task
  - CLS ≤ 0.05

  Baselines are in private Lighthouse files (not in repo; re-measure).
- **Visual diffs of the maths:**
  - Use `tools/visual_check.py` (already in the repo; `--site _site --screenshots`) or Playwright. Screenshot 20 maths-heavy pages (top 20 by span count) at 390 px and 1280 px, in light and dark, before (current main) and after (PR build).
  - Pixel-diff them (e.g. `pixelmatch`); differences above 0.1% go to manual review.
  - Also diff the DOM `textContent` of `.katex-mathml` on 5 pages against a client-rendered copy (`katex.render` in headless Chrome). They should be identical.
- **Failing-macro pages:** confirm `\E`, `\Var` and `\Cov` render on `articles/cauchy-schwarz-inequality.html` and the other affected pages, with no `.katex-error` elements anywhere: `grep -c katex-error` over `_site` should be 0.
- **Glossary split:** recrawl and check that every former glossary term appears on exactly one letter page, all letter pages are in the sitemap, and no internal link 404s.
